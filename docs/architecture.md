# Phase 2 Architecture

The browser-facing Next.js application submits one source type to the FastAPI service. Articles are not persisted.

```text
Text / URL / PDF → ingestion route → extraction & normalization → language + metadata
                                                              ↓
Dashboard ← structured response ← POST /api/analyze/article ← analysis service
                                                       ↓
segment/tokenize + optional local XLM-RoBERTa classifiers + Groq contextual analysis
         (sentiment / NER only, when configured)          (active framing provider)
                                                       ↓
       validated exact original-text spans, attribution, assessment, provider status
```

The Phase 1 ingestion routes remain responsible for safe URL/PDF/text extraction. The dashboard then passes their `extracted_text` to the analysis endpoint, preserving paste, URL, and PDF workflows.

XLM-RoBERTa is retained for optional, task-specific local sentiment and named-entity classifiers in `MODEL_CATALOG`; those pipelines run only when their catalogued model IDs are configured. They do not perform contextual bias or framing analysis. Groq GPT-OSS 120B (the default configured model) is the active provider for that contextual analysis. Its status and model are returned through the existing API response and shown in the dashboard. No XLM-RoBERTa weights are loaded just to represent this architecture.

Task-specific language routing remains explicit. The CardiffNLP sentiment checkpoint documents English and Hindi, the Hartmann DistilRoBERTa emotion checkpoint documents English, and Davlan XLM-R NER documents English among this application's five languages. The MuRIL/Naamapadam NER checkpoint `vaibhav006/indic-ner-muril-naamapadam` is routed for Telugu only; its card reports Telugu F1 0.8328 on its own evaluation data, not this application's news domain. It predicts PER/ORG/LOC. Hindi, Kannada, and Tamil NER remain unsupported by these selected task checkpoints. The separate ONNX IndicNER derivative has broader language tags but an ONNX-specific runtime and tokenizer details; the tags alone are not treated as verified task evaluation for all those languages.

The examined `ai4bharat/IndicBERTv2-MLM-only` checkpoint is pretrained for masked-language modeling, not fine-tuned sentiment or emotion. It is not used as a classifier. The examined multilingual sentiment candidate `tabularisai/multilingual-sentiment-analysis` lists Telugu among many languages but uses synthetic data, carries a CC-BY-NC-4.0 license, and does not document Kannada or Tamil; it is not silently selected. `tabularisai/multilingual-emotion-classification` lists Hindi and Tamil but has similar synthetic-data/non-commercial caveats and is not selected as verified local emotion inference. These task-model cards establish intended/documented scope, not multilingual news accuracy.

When local sentiment or emotion is not available, `analysis_service` requests an optional fallback field in the same Groq contextual response. This does not add a second Groq request. Fallback schemas have fixed label sets and require exact article quote validation for detected labels; uncertainty/not-detectable outcomes may omit a quote. A local emotion prediction takes precedence. Sentiment and emotion remain separate from the bias score. NER stays local and has no provider fallback. The Groq report includes whether the request was made or a cache hit reused.

Successful Groq JSON responses use a bounded process-local LRU/TTL cache (defaults: 128 entries, 1,800 seconds). Cache keys use a SHA-256 digest of exact normalized article text plus language, model, prompt/schema version, maximum input length, and optional fallback flags. Titles and API keys are not in cache keys. Cache data is not shared across worker processes or restarts; it can avoid repeated equivalent calls but does not guarantee cost elimination. Setting `GROQ_CACHE_TTL_SECONDS=0` disables it.

`overall_judgment` is produced within the existing analysis response. Its provisional directional-framing indicator requires at least 80 whitespace-delimited tokens, four distinct validated Groq findings, three authorial/unattributed directional findings, 1.5 weighted evidence units, and a successful contextual response. Each eligible distinct span contributes model confidence (0.6 when absent) × attribution weight (0.8 for journalist narration, 0.5 for unattributed claim). Duplicate offsets count once. The displayed value is absolute positive/negative weight imbalance × `min(1, eligible_findings / 5)` × mean confidence × 100. Attributed quotes are omitted from scoring. The threshold/formula is an internal provisional heuristic, not a calibrated probability or validated bias measure. Sentiment and emotion do not contribute. Below the threshold the API returns `insufficient_evidence` and no indicator.

`analysis_service` never translates input. It uses punctuation-based segmentation, whitespace tokenization, conservative English date/person-candidate rules, optional task-specific Transformers models, and evidence helpers. Evidence quotes are direct slices of `original_text` using returned Unicode character offsets. Sentiment and emotion are separate classifier tasks; no label is inferred from a missing lexicon hit. A configured local checkpoint directory can be supplied per task (`SENTIMENT_MODEL_PATH`, `EMOTION_MODEL_PATH`, or `NER_MODEL_PATH`) alongside that task's exact catalogued model ID. Loading remains local-only, and the path must contain the named checkpoint.

The contextual bias/framing path is `analysis_service.analyse_article` → `GroqFramingService.analyze` → Groq Chat Completions through the official Python SDK → strict JSON/Pydantic validation → quote validation against the original text → existing `BiasAssessment` response fields → frontend framing panel. The client is only created when a primary key and supported target-language code are available. API keys remain server-side.

Primary/backup failover is limited to authentication/permission/rate-limit and transient network/server failures. Authentication and 429 errors switch immediately to the backup; timeouts/network/5xx errors may retry the same key up to the configured count before backup. Bad model/request errors do not rotate credentials. SDK-level retries are disabled so the application controls the bound. Public errors are generic and logs contain only key slot, exception type, and HTTP status—never the key or raw provider body.

Inputs below the configured maximum are analyzed in full. Longer articles use bounded beginning/middle/end excerpts, separated by an explicit omission marker; any returned findings must still quote exact contiguous spans in the full original article. Responses label this `sampled_excerpts`, disclose partial coverage, and do not claim a whole-article assessment. Invalid JSON, unsupported categories, invalid confidence values, empty responses, or wholly unverifiable findings produce `unavailable`, never a successful placeholder.

## Verified model scope

Offline local inference was exercised on Python 3.14.3, Transformers 5.14.1, and CPU Torch 2.10.0: CardiffNLP sentiment on English and Hindi, Hartmann emotion on English, and Davlan NER on English. The end-to-end English analysis path also returned model-backed results with original-text offsets. These single-input smoke checks establish loading and code-path behavior only, not news-domain accuracy. Hindi was exercised only for sentiment. The Telugu MuRIL NER path is tested with mocked model outputs; Telugu model weights were not downloaded or inferred in this application. No trained contextual-framing, POS, sarcasm, or code-switching model is configured; Kannada and Tamil remain unsupported by the selected local classifiers. The small deterministic fixtures exercise language identification and API/status behavior for the five target languages; they are not native-reviewed framing benchmarks and do not support precision/recall claims. Exact candidate metadata and remaining limitations are below.

Phase 3 extends the same response with a `statistics` report: raw category counts, sentence/token counts, model-backed sentiment distribution only when inference succeeds, and an evidence-per-1,000-token rate. The rate is normalisation for comparison only, never a bias score. The evidence validator rejects any span whose bounds or quote fail to match `original_text` exactly.

Evidence records are deduplicated per category so repeated wording is one finding with an occurrence count, while `occurrence_spans` and `contexts` retain every counted position and sentence. Sentence-level rules anchor on a predicate token rather than the whole sentence, which keeps highlights precise and non-overlapping. `evidence_strength` names the matching method and is not a confidence probability.

Every analysis response includes per-task availability, including language identification, sentiment, emotion, NER, POS, contextual framing, sarcasm, code-switching, transliteration, and cross-language semantic matching. Contextual framing reports `available`, `not_configured`, or `unavailable`, and only Groq-generated findings enter the article-level `bias_assessment`. Sparse legacy indicators are returned separately as auxiliary lexical/phrase cues and never determine that assessment. Every model finding contains an exact contiguous quote, verified Python Unicode-character offsets, attribution type, actor/speaker where available, contextual explanation, alternative interpretation, uncertainty, and confidence. Empty findings are allowed; missing findings are not a neutrality claim. Groq analysis is model-generated text analysis, not independent fact-checking or proof of author intent. The prompt covers English, Hindi, Kannada, Telugu, and Tamil, but mocked language-contract tests do not establish real-world competence. Sarcasm, slang, code-switching, and cultural interpretation remain fallible. A single article cannot establish selective presentation, source balance, or omitted context.

The existing URL service resolves every hostname before each request/redirect, blocks non-global addresses, bounds response sizes, and extracts readable HTML only. It does not bypass paywalls or authentication.

Phase 4 adds `POST /api/compare/article`. `comparison_service` generates entity/keyword queries, issues one bounded GDELT request covering all requested source languages plus one Google News RSS request per language, deduplicates URLs, and only then uses the existing safe URL extractor with bounded concurrency. `provider_status` separates an empty provider result from a timeout, rate limit, HTTP error, or invalid response, and a failed provider never disables the other. A deterministic same-event verifier returns rationale and an uncalibrated relevance signal. The existing analysis service runs only over available candidate text; the comparison response separates full-text, snippet-only, and metadata-only coverage and preserves provider failures as partial results.

## Phase 5: deterministic evaluation and reliability boundaries

`backend/evaluation/fixtures.json` is deliberately separate from application code and spreadsheets. `python -m evaluation.run --output evaluation-report.json` runs the analysis service and same-event verifier only against these reviewed, deterministic inputs. It does not call GDELT, Google News, or article URLs. The report identifies exact-span validation failures, language-case coverage, feature availability, comparison verification outcomes, errors, skips, and a clearly scoped fixture-only matching metric.

Evidence is fail-closed at the analysis boundary: a span must have `0 <= start < end <= len(original_text)` and an exact `original_text[start:end] == quote` match. The frontend independently declines invalid spans. The offset convention is Unicode code-point indexing as used by Python strings and JavaScript string slicing for BMP Indic text; callers should preserve the returned original text rather than normalize it again.

Comparison results use explicit verification states: `verified_match` for sufficient full-text rule evidence, `possible_match` for lower-confidence or snippet-only similarity, `rejected_match` for a conflicting date or weak full-text similarity, and `insufficient_evidence` where the system cannot decide. Scores are diagnostic relevance signals only. Coverage is bounded, partial, and must never be interpreted as exhaustive or as a statement about a source, language, or article's bias.

## Phase 7: research reporting and PDF export

`POST /api/reports/pdf` accepts the typed `ArticleAnalysisResponse` previously returned by `/api/analyze/article`, plus an optional `ComparisonResponse` previously returned by `/api/compare/article`. The route serializes those results without rerunning analysis or contacting discovery providers. It validates exact evidence spans, bounds article text to 100,000 Unicode characters, limits evidence to 5,000 spans and comparison candidates to 100, and rejects a serialized request over 5 MB. Successful responses use `application/pdf` and an attachment filename; validation failures use FastAPI's `422` response and rendering failures return a generic `500` message without internal exception details.

`report_service` composes the supplied outputs into a paginated A4 PDF with headings, tables, evidence grouped by category, generated-at metadata, source attribution, and page numbering. It reports punctuation-based approximate sentences, whitespace-delimited tokens, distinct finding counts with occurrence counts and explicit denominators, and evidence density as separate quantities. A generated summary and publication date are not available in current analysis/ingestion results and are labelled unavailable. URL credentials, query strings, and fragments are omitted from printed URLs. Empty entity results, unsupported analyses, absent comparisons, and missing language coverage are not presented as fabricated zeroes or findings.

The dashboard uses its current analysis and includes comparison data only when present. A report-generation failure is displayed separately and does not clear the analysis or comparison state. The download utility is covered by a deterministic Node built-in test. A browser end-to-end test suite is not currently configured.

The backend depends on `PyMuPDF`, `pymupdf-fonts`, `fpdf2`, and `uharfbuzz`. Noto Sans resources and HarfBuzz provide report typography and shaping; no large font assets are committed. Windows uses the installed Nirmala UI collection, while Linux deployments should install the matching Noto Sans font for the article script. The evidence appendix was visually inspected with Nirmala UI for Hindi, Kannada, Telugu, and Tamil; visual behavior still depends on the installed font and PDF viewer. A UTF-8 evidence attachment preserves exact quotations independently of viewer text extraction. If a suitable system font is absent, the report states that the shaped appendix is unavailable and retains the attachment fallback. Visually inspect PDFs before publication. Reports explain that lexical/rule indicators are observations rather than proof of intent or definitive bias.

## Phase 10: quality, evidence, and reporting refinements

The analysis engine reports one finding per observable cue. It no longer emits a derived `potentially_one_sided_framing_cue` duplicate or a bare-predicate `unattributed_assertion_candidate`. Each finding carries a `claim_status` (`attributed`, `unattributed`, `attribution_marker`, or `mixed`) describing the configured attribution marker in its anchor sentence. This is a coverage observation, not a truth or source-quality judgment. A `methodology` block exposes the category and claim-status definitions used by the dashboard and report, and `statistics.attribution_summary` documents the claim-status denominator.

Same-event verification requires retrieved full text, at least two shared body event terms (named entities alone are insufficient), and a sufficient rule score before returning `verified_match`. Snippet-only candidates can only be `possible_match`, `rejected_match`, or `insufficient_evidence`. Google News RSS redirect links are treated as snippet-only because a server-side fetch returns an interstitial rather than the publisher article. Cross-article wording counts include only verified full-text matches.

The PDF report includes the provisional overall bias/framing judgment when available, preserves an explicit insufficient-evidence state, and labels the indicator as uncalibrated. The cross-language comparison starts on a fresh page so coverage observations and provider status are not clipped by preceding report content. Reports also include an executive summary, methodology and indicator definitions, claim-status context on evidence, and a concise evidence-preservation section. They retain the paginated evidence appendix and UTF-8 attachment for Indic scripts. The dashboard groups evidence by category, uses readable labels, shows claim-status badges, collapses technical detail, and separates matched comparison candidates from other evaluated candidates.

## Optional model runtime and verified scope

The `MultilingualModelManager` accepts only reviewed model IDs from `MODEL_CATALOG`. It loads Hugging Face model/tokenizer files with `local_files_only=True`, uses CPU inference, truncates model inputs to 512 tokens, limits each analysis to `max_model_sentences` (default 32) and `max_model_input_chars` (default 4,000), and keeps at most one model pipeline resident per manager. Before loading it checks available RAM with `psutil` and requires approximately twice the checkpoint weight size free; this is a conservative guard, not a guarantee against operating-system memory pressure. There is no model download during application startup or request handling. Set `SENTIMENT_MODEL_ID`, `EMOTION_MODEL_ID`, and/or `NER_MODEL_ID` to enable a catalogued task; optional `*_MODEL_PATH` settings point to a local directory containing that checkpoint. `not_configured`, unsupported pairs, missing local files (`model_unavailable`), and loading/inference failures are reported distinctly.

### Indic and cross-language model choices

- `google/muril-base-cased` is Apache-2.0 and pretrained on 17 Indian languages plus transliterated counterparts. Its published data includes translated/transliterated pairs and its paper reports downstream POS/NER benchmark results after task fine-tuning. The downloaded checkpoint is a masked-language-model (`BertForMaskedLM`), not a ready sentiment, emotion, NER, POS, sarcasm, or framing classifier; therefore it is not activated as any of those tasks.
- `ai4bharat/IndicBERTv2-MLM-only` has 278M parameters and is described for 23 Indic languages plus English. This checkpoint is also MLM-pretrained; task-specific fine-tuning and per-language evaluation are required. No task-finetuned checkpoint was selected or tested here.
- [`sentence-transformers/LaBSE`](https://huggingface.co/sentence-transformers/LaBSE) is Apache-2.0 and maps 109 languages (including en, hi, kn, te, ta) into a sentence-similarity space. It has about 471M parameters and roughly 1.8 GiB of FP32 weights. It is not integrated or installed here; it would need `sentence-transformers` and substantial memory. Similarity would support only cross-language matching, not sentiment, bias, actor portrayal, or selective presentation.
- XLM-RoBERTa and multilingual encoders are architectures, not bias detectors. The configured XLM-R-derived classifiers are used only for the specific sentiment or NER objectives on which they were fine-tuned.

### Capability and evaluation boundaries

The tested language identifier recognizes clean English/native-script fixtures for en, hi, kn, te, and ta; this does not verify sentence-level code switching, Latin transliteration, or short-text accuracy. The deterministic suite validates response/status behavior and exact evidence offsets, not model accuracy. In addition to controlled fake-pipeline tests, offline smoke checks exercised the cached sentiment checkpoint on English and Hindi, and the emotion and NER checkpoints on English (see verified model scope above); these do not establish classifier quality. No dedicated sarcasm/irony classifier is configured. Groq's contextual prompt accepts en, hi, kn, te, and ta, but live-provider accuracy in those languages has not been independently evaluated; sarcasm and colloquial/cultural interpretation remain fallible. Mixed-language spans, POS tagging, and cross-language semantic matching are not supported. The legacy `embedding_model_id` setting is not consumed: if supplied, capability status is `inconclusive` and no embedding inference is attempted. An empty finding list is not presented as an overall unbiased conclusion.
